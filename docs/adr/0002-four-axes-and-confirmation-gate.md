# ADR 0002 — 知识条目四轴解耦 + 确认唯一闸门 + 检索按类型分裂

## 状态

已接受（本轮 grilling 会话）

## 背景

ADR 0001 确立了 EvoKit 的"项目上下文引擎"方向后，领域模型中的知识条目字段隐含耦合、语义模糊。打磨中发现三处结构性问题：

1. **type 与 scope 隐含耦合** — 模型暗示 `preference`↔个人、`convention`→项目，但真实情况是"同一偏好因项目而异"、"convention 也可能是个人习惯"。
2. **confidence 有字段无语义** — frontmatter 必填 `0.0–1.0`，但模型未定义它代表什么、如何变化。既经人工确认，它不可能继续当"可信度"。
3. **检索盲区** — 只有 `knowledge-index.md` 摘要常驻、条目按需加载。但架构型知识的结论依赖推理链，光看摘要 AI 不会知道何时该加载对应条目。
4. **source 与前提冲突** — git-history 被标为"自动提取"，直接进 `knowledge/`，绕过确认，违反"已确认 → 可高置信"的前提。

## 决策

将知识条目理解还原为**四根正交轴 + 一条不变量**：

| 轴 | 语义 | 判据 |
|----|------|------|
| **type** | 内容讲什么 | `convention`（微观/可反推）vs `architecture`（结构/猜不出）；`preference`·`workflow` 独立。判据：AI 光看代码能否猜出。 |
| **scope** | 归属（个人/项目） | "换到另一个项目还成立吗"→个人/项目。**type≠scope**，二者解耦。 |
| **source** | 从哪捕捉 | conversation / explicit / git-history |
| **confidence** | 时间寿命 | **维护/新鲜度信号，非可信度**：初始固定高（0.9，因已确认），随过期检测下降，低阈值触发复审。 |

**不变量：入库必经人工背书，无"直接写入"例外。** 对话提取 / git-history 先进 `.pending/`、经确认流程人工确认后入库；显式声明是用户发起即**当场背书**直接入库（最强背书形态，非闸门反例）。

### 机制修订

- `.pending/` 一律按当前项目存放；`scope` 在**确认时**人工裁定（对话提取），显式声明时用户带 scope（缺省当前项目），两条路径统一。
- git-history 从"自动"改为"提出候选 + 确认"。
- **检索按类型分裂**：规则型（convention/preference/workflow）摘要即知识、索引常驻已足够；架构型（architecture）需正文带推理标注（影响范围/相关决策），AI 遇模块依赖/服务划分/数据流话题时主动追索。

## 取舍

### 选择 scope 确认时裁定，而非识别时猜测

- **放弃**：识别即定型的高效
- **获得**：scope 高质量（人工裁，而非 AI 在单对话里瞎猜）
- **代价**：确认流程从"确认/拒绝"扩展为"确认+定作用域/拒绝"，多一步交互

### 选择 confidence 为维护信号而非可信度

- **放弃**：统一的"可信度"度量
- **获得**：与"已确认即可信"不矛盾，给模型补上缺失的**时间轴**
- **代价**：需为过期检测定义具体降分规则（见下）

> **展开：confidence 离散三档状态机**（已定稿）
> 触发是二分判断（"这条还成立吗"），落档是指定值——AI 不需精确打分：
> `0.9 已确认且有效 → 0.5 待复审 → 0.1 疑失效`。
> 降分只来自过期检测；≤0.5 进 `/evokit-review` 复审名单，0.1 交用户定留/删，复审有效可回升 0.9。

### 选择 git-history 也过确认（方案甲），而非低初始 confidence（方案乙）

- **放弃**：git-history 全自动的高省心度
- **获得**：保住了"确认是唯一入库闸门 + confidence 高值无条件成立"这条最干净的不变量，规则少一条
- **代价**：git 提取多在确认流程里过一道

### 选择检索按类型分裂，而非统一摘要索引

- **放弃**：索引形式统一的美观
- **获得**：架构型知识真正被检索到，不再是从不被想起的死知识
- **代价**：架构条目需写推理标注，比规则条目重
