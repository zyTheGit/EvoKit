# ADR 0005 — 助手间冲突合并用"事后健康诊断"，非实时协商

## 状态

已接受（本轮 grilling 会话）

## 背景

CONTEXT.md（v1.0）把"助手间同条目**实时**协商/冲突合并"留到 v1.x，但未定义场景与机制。本轮 grilling 核对实现后发现三处决定性事实：

1. **对话提取写 `.pending/` 是 AI 直接写文件，零代码护栏**（`template/claude/CLAUDE.md`、`learning-recorder/SKILL.md` 指令驱动）；TS 代码（`createDraft`）只服务 git-history 这一条路径。
2. **确认流程也是 AI 直接挪文件**（`/evokit-learn` 命令文档："执行操作：确认的移入 `knowledge/` 并更新索引"），不经过 `KnowledgeRepository.confirmDraft` 代码——该代码只服务终端交互式 `evokit learn` 用户。故对话提取路径上**没有代码 chokepoint 可注入写入时/确认时去重**。
3. **多助手并发写无任何锁**：`confirmDraft` 不查 `knowledge/` 已有同 id/相似条目（静默覆盖，TOCTOU）；索引 `appendIndex` 是非原子 read-modify-write，并发确认丢行（last-writer-wins）。

同时"实时"措辞与核心承诺冲突：实时跨助手协调需要常驻进程/IPC，违反 ADR 0001"零遥测、全本地存储"。

## 决策

将"助手间冲突合并"落地为**事后健康诊断 + 人工合并**，**非实时协商**。修正 CONTEXT.md 的"实时"措辞。

> **决策理由（v1.2 评审会议三人一致要求重写）**：背景事实只证明**对话提取/确认是 AI 直接写挪文件、无代码 chokepoint 可注入**，并不逻辑排除替代方案（改 skill 强制走 `evokit learn confirm` CLI、加文件锁等）。本 ADR 不把"碰了也强制不了"当事实结论，而是**显式取舍**：v1.2 范围内选择不修改 AI-direct skill/命令协议（改它要动 v1.0 已稳定的 `/evokit-learn` + `learning-recorder` 形状，成本/风险不在 v1.2 预算内），故事后诊断是 v1.2 范围内**唯一收敛点**。`confirmDraft`（终端 CLI 路径）是真实 chokepoint，在其内复用 `findSimilarActive` 做确认时查重提示是廉价纵深防御——列为 **Won't-do（推后）**：`evokit learn confirm` 非交互子命令 + confirmDraft 内查重，单列 v1.2.x 或 v1.3 增量，不混入本设计 ADR。

1. **归一化全等重复检测（Normalized Exact-Duplicate Detection）** — **非"近重复"**：归一化全等（复用 `normalizeKnowledgeText`：小写 + 去空白 + 去标点后**整段全等**）判定重复条目，作为知识库健康指标由 `evokit doctor` / `evokit boot` 表面化。与 v1.1 已发布的索引漂移检测**同构**。
   - **比较字段**：`context`（摘要）→ `body`（正文，剥 markdown 标题行）→ `id`，按显式声明路径 `findSimilarActive` 既有优先级，**逐一归一化全等**比较（非相似度阈值、非编辑距离）。
   - **≠ 语义近重复**：措辞不同但语义相同的重复（"使用 pnpm" vs "包管理器用 pnpm"）**漏报**；语义/模糊近似检测**显式推 v1.3**，不在 v1.2。
   - **已知误报边界**：极短正文（一句话 tip / 常见命令片段）归一化撞车可能误报——防线是**人工三选**，非归一化本身；ADR 不声称零误合。
   - **检测宇宙**：`pending↔pending`、`pending↔active`、`active↔active` 全覆盖，但**作用域内**（见 C3）。
2. **合并 = 人工三选，代码不自动合并** — 复用显式声明路径"三选"语义（合并为主条刷新正文 / 保留两条 / 择一保留），由用户裁定，复用 `overwriteActiveBody`。守"人工背书唯一闸门"+ 避免错合。**合并合同见下"合并执行契约"。**
3. **`doctor --fix` 对冲突的行为：逐条列出，永不自动择主** — `--fix` 在冲突合并上**仅排队/列出冲突对供逐条人工三选**，**绝不**自动选主条、绝不批量自动合并（与"重建索引"的 `--fix` 同名但子模式不同，须文档化子模式区分）。删去原"批量合并入口"歧义措辞。
4. **不做实时** — 不引入 daemon/IPC/锁协调跨助手会话；冲突在下次 `boot`/`doctor` 时被发现并提示合并。
5. **索引写入硬化 = Non-goal 旁路（剥离为独立 hotfix）** — 索引 `appendIndex`/`writeKnowledgeIndex` 改用 `atomicWriteFile` 是**既有竞态 bug fix**，与冲突合并设计**正交**，应作为独立 hotfix PR/CHANGELOG 条目，本 ADR 仅引用其存在为前置依赖。**明确：原子写只防单写者损坏/半截写，不消除多助手 last-writer-wins 丢行（TOCTOU 窗口仍在），并发丢更新仍靠 `regenerateIndex` 全量重建事后收敛——而 `regenerateIndex` 依赖"有人跑 doctor/boot"**。读者不应理解为"原子写 = 并发安全"。

### 合并执行契约（评审要求补齐的可实施合同）

- **冲突键**：`归一化全等 + 同 type`；不要求 id 相同（id 不同内容全等 = 典型冲突；id 相同内容不同 = 静默覆盖残骸，另案）。
- **三选每支对文件 + 索引的突变**：
  - "合并为主条"：`overwriteActiveBody` 刷新主条正文 + `updated`，**删除从条文件** + `removeIndexEntry` 删其索引行；
  - "保留两条"：不动；
  - "择一保留"：删弃条文件 + 删其索引行。
- **孤儿同步**：合并后必须同步删除被弃条目文件**及其索引行**——`overwriteActiveBody` 若不更新索引元数据则需补 `removeIndexEntry` 调用；**审计前置依赖**（见 C7）。
- **跨作用域**：见下。

### 作用域与跨作用域（C3）

检测/合并**仅限同作用域内**：个人级（`~/.evokit/knowledge/`）与项目级（`.evokit/`）**分别**跑归一化全等扫描，**不做跨层合并**。一条个人级与一条项目级条目归一化全等不判为冲突——它们本就可能在不同语境各自成立。跨层迁移/提升是独立操作（先手动迁条目再合并），不在 v1.2 冲突合并范围内。

### 作用域

仅"助手间同条目冲突合并"（单用户多助手，存储拓扑不变：`~/.evokit/` + `.evokit/`）。**团队级知识共享推 v1.3+**（多用户、新存储拓扑 + 权限模型，独立 ADR）。

## 取舍

### 选择"事后诊断"而非"实时协商"

- **放弃**：实时性（冲突产生即被发现/协调）
- **获得**：不违反"本地优先、零 daemon"；复用 v1.1 健康诊断机制（`normalizeKnowledgeText` + `findSimilarActive` + `doctor`/`boot` 表面化 + `--fix`）；与 ADR 0003"健康诊断表面化而非自动降档"哲学一致；不触碰 AI-direct 写入路径
- **代价**：冲突在被发现前可能短暂同时存在于 `knowledge/`，靠下次 `boot`/`doctor` 收敛；用户若长期只用助手会话、从不跑 CLI，冲突可长期并存并污染检索/注入上下文。**"冲突是低频事件"是待验证假设非既成事实**——多助手并行会话恰是 EvoKit 卖点场景，onboarding/重构期冲突频率可能被低估。设回顾条件：**v1.2 发布 30 天内若 `doctor` 报告冲突数 > 阈值 N（待定），触发本 ADR 复审**（可能需在 session 启动注入中提示重复健康项，仍无 daemon，仅文档/模板钩子）。

### 选择"归一化全等"而非"embedding 语义去重"

- **放弃**：捕捉措辞不同但语义相同的重复
- **获得**：确定性、零模型依赖、可解释；与 ADR 0003 已明确的"不做 embedding 语义过期检测"一致；与显式声明路径现有去重一致（同一把尺子量两个入口）
- **代价**：措辞差异大的同义重复漏报（"漏提优于误提"，与 ADR 0004 research note §3.5 同一总原则）

### 选择"人工三选合并"而非"自动合并"

- **放弃**：全自动合并的省心度
- **获得**：守"人工背书唯一闸门"不变量；避免代码错合两条本就不同但归一化恰好全等的条目
- **代价**：每处冲突需用户点一下（与确认闸门同一交互成本）

### 选择"AI-direct 写入路径不强制"而非"改 AI 走代码确认"

- **放弃**：写入/确认时点的实时拦截
- **获得**：不改 v1.0 已稳定的 `/evokit-learn` skill 与 `learning-recorder` 指令形状；事后诊断对"AI 直接挪文件"这一现实完全免疫
- **代价**：放弃了一道理论上的预防层；由事后诊断兜底

## 前置依赖与验收条件（C7）

本 ADR 复用四个既有件，**实现前必须先审计其契约**，否则会悄悄分叉：

| 件 | 假设 | 审计点 | 若不匹配 |
|---|---|---|---|
| `normalizeKnowledgeText` | 小写+去空白+去标点 | 规则是否如 ADR 0002 所述 | 补齐规则 |
| `findSimilarActive` | 扫 `active`（已入库），归一化**全等**非相似分 | 是否只扫 active？是否全等？比较字段优先级？ | 若是相似分/编辑距离，复用会改变显式声明路径行为 → **须先审计，不可直接复用**；可能需新增 `findExactDuplicates(扫 active+pending)` |
| `overwriteActiveBody` | 刷正文 + `updated`，不动 id/索引行 | 是否更新索引元数据？是否删从条？ | 合并合同要求补 `removeIndexEntry` 调用 |
| `atomicWriteFile` | tmp→validate→backup→rename | 语义匹配 | — |

**验收条件**：
1. 近重复检测单元测试：同 type 归一化全等命中；不同 type 不命中；id 不同内容全等命中；id 相同内容不同**另案不混入**。
2. 三选合并测试：每支的文件 + 索引行突变正确，无孤儿。
3. 跨作用域：个人↔项目归一化全等**不**判为冲突。
4. `--fix` 冲突子模式：仅逐条列出，无自动选主路径可达（防回退断言）。
5. 索引原子写 hotfix 独立 PR，不与本 ADR 实现绑定。
6. 在现有 `knowledge/` 上跑一遍统计误报率，作为"归一化全等"的基线证据（回应 C2）。

## 边界与已知限制（评审补齐）

- **AI-direct 索引损坏检测盲区**：`atomicWriteFile` 只覆盖 CLI 代码路径；AI 直接编辑索引文件产生的损坏不在原子写保护内。`doctor` 须含索引结构完整性校验（frontmatter 合法 + 条目存在性交叉验证），或承认此路径为 v1.2 已知限制。
- **同 id 异文（静默覆盖残骸）**：`confirmDraft` 不查同 id → 两条同 id 不同正文，后者静默覆盖前者。本 ADR 的归一化全等检测针对**内容全等**，**同 id 异文是另一类冲突**，v1.2 不合并处理，列为已知限制。
- **极短正文误报**：见决策 §1 已知误报边界，靠人工三选兜底。
- **多机/多 clone 同一 `~/.evokit` 交互**：单用户多机的知识根同步超出 v1.2（属团队级 v1.3+ 边界）。
